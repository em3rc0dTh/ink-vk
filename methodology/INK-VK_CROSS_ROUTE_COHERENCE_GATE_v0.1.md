# Ink-VK — Cross-Route Coherence Gate v0.1

**Status:** PROPOSED / METHODOLOGY  
**Date:** 2026-08-14  
**Learning source:** VTKALL × Dayos consolidated blueprint

---

# 1. Problem

Route-level transformation contracts can all be individually valid while the final product is globally incoherent.

Example failure:

```text
HOME passes truth / fidelity
SOLUTIONS passes truth / fidelity
DEMONSTRATIONS passes truth / fidelity
METHOD passes truth / fidelity
COMPANY passes truth / fidelity
START passes truth / fidelity

BUT

all six pages use the same dramatic 3D hero
all six repeat the same card grid
navigation implies children that do not exist
proof status changes from route to route
density is inconsistent with user job
CTA / footer rhythm changes arbitrarily
```

Local correctness is therefore necessary but insufficient.

Governing rule:

> **A route may be valid alone and still fail the system when composed with its peers.**

---

# 2. Purpose

The Cross-Route Coherence Gate validates the product as a system before PLAN.

It asks:

```text
Do the admitted routes behave like members of one experience system
without being flattened into one generic template?
```

This gate is most relevant when the target has:

```text
multiple routes
multiple donor page modes
multiple density modes
multiple proof types
multiple interaction depths
```

---

# 3. Coherence is not uniformity

Incorrect interpretation:

```text
COHERENCE
=
SAME HERO
SAME CARD
SAME SECTION ORDER
SAME DENSITY
SAME 3D
```

Correct interpretation:

```text
COHERENCE
=
SHARED SYSTEM RULES
+
PURPOSEFUL PAGE-MODE VARIATION
```

Shared rules may include:

```text
global shell
surface grammar
typographic roles
status language
spacing logic
motion hierarchy
brand expression
closure rhythm
```

Variation may include:

```text
section topology
content density
primary visual device
local navigation
proof mechanism
interaction model
```

# 5. Coherence dimensions

## C1 — Global shell

Check:

```text
brand placement
navigation grammar
primary action
footer grammar
route reachability
```

A route must not invent global shell behavior privately.

## C2 — Page-mode differentiation

Each route must have a page mode justified by its information job.

If every route becomes the same template, donor intelligence has been flattened.

## C3 — Surface grammar

Shared surface states should mean similar things across routes.

Example:

```text
DARK
= assertion / manifesto / strong route opener / evidence state
```

not random decoration.

## C4 — Density allocation

Density follows purpose.

```text
library / matrix / pattern discovery → denser
manifesto / single-task / major claim → more isolated
```

Do not normalize all routes to the same vertical spacing.

## C5 — Signature-device allocation

Strong devices need semantic ownership.

Examples:

```text
major 3D
connected timeline
filter rail
team photography
full-screen form
```

A signature device should recur only where the same job exists.

## C6 — Proof/status consistency

The same evidence class should not receive contradictory labels across routes.

Example:

```text
Turagua
DEMONSTRATION on one route
CUSTOMER SUCCESS on another
```

is a system failure.

## C7 — Interaction-depth consistency

Controls with similar appearance should make similar promises.

A disabled/static preparation field should not visually imitate a fully operational form unless its status is unmistakable.

## C8 — Motion hierarchy

Motion classes should have stable semantic jobs.

Do not use dramatic movement everywhere.

## C9 — Responsive continuity

When routes collapse differently on smaller screens, the system should still preserve:

```text
shared navigation
status grammar
typographic hierarchy
surface meaning
closure behavior
```

## C10 — Closure rhythm

Every route should resolve:

```text
CONTENT
→ ACTION
→ FOOTER
```

without forcing identical CTA copy.

# 6. Signature-device allocation rule

Donor systems often have several memorable devices.

If every route receives every device, the target becomes noisy and semantically weak.

Use:

```text
DEVICE
↓
DONOR JOB
↓
TARGET ROUTE JOB
↓
OWNER / SHARED / NOT USED
```

Possible dispositions:

```text
OWNER
SHARED GRAMMAR
CONTEXTUAL
NOT APPLICABLE
DEFER
```

Example from VTKALL × Dayos:

```text
MAJOR 3D            → HOME OWNER
DENSE PATTERN SCAN  → SOLUTIONS OWNER
EXPLICIT STATUS     → DEMONSTRATIONS OWNER
CONNECTED PROCESS   → METHOD OWNER
EDITORIAL RAIL      → COMPANY OWNER
SINGLE-TASK FOCUS   → START OWNER
ROUNDED HANDOFF     → SHARED GRAMMAR
DARK OPENER         → SHARED GRAMMAR
```

---

# 7. Repetition test

For each repeated device ask:

```text
1. Is the semantic job the same?
2. Does repetition strengthen system recognition?
3. Does repetition reduce route differentiation?
4. Is the donor actually repetitive here, or are we overgeneralizing?
5. Is the target truth/capacity valid on every route where it appears?
```

If the answer to 1 or 5 is NO, remove or reinterpret the repetition.

---

# 8. Collision test

Cross-route collisions include:

```text
same content repeated without new job
same evidence presented under different status
same CTA meaning labeled differently
same interaction styled identically but with different capability
same visual device implying incompatible semantics
navigation route duplicated as both ordinary and primary action without reason
```

Resolve collisions before PLAN.

---

# 9. Cross-route truth consistency

A target fact has one public status unless new evidence explicitly changes it.

Create a shared truth vocabulary for recurring entities/concepts:

```text
DEMONSTRATION
PATTERN
PRODUCT
PARTNER
CUSTOMER
STATIC
ACTIVE
```

No route may independently upgrade status.

---

# 10. Cross-route non-regression

A known target defect may appear in more than one route.

Global defects should be inherited by every relevant blueprint.

Example:

```text
crowded center + unused sides
section leakage
clipping
CTA/footer collapse
```

The Cross-Route Gate checks that route-specific redesigns did not solve the problem on one page and recreate it on another.

# 11. Relationship with existing gates

## Target Truth

```text
Is the content/state legitimate?
```

## Content Capacity

```text
Is there enough real content/state for the mechanism?
```

## Non-Regression

```text
Are known target failures prevented?
```

## Donor Job Decomposition

```text
Which donor jobs are actually being transferred?
```

## Cross-Route Coherence

```text
Do the valid route decisions compose into one intentional system?
```

The Cross-Route Gate does not replace earlier gates.

It evaluates their composition.

# 13. Framework placement

Do **not** create a new macro phase.

Cross-Route Coherence belongs primarily inside:

```text
STEP 18 — DESIGN TARGET BLUEPRINT
```

and later validation inside:

```text
STEP 25 — MODE-AWARE VK TEST
```

It may also inform PLAN slicing because page-family boundaries become clearer.

# 14. VTKALL × Dayos learning

The case produced six valid page modes:

```text
Home            → narrative choreography
Solutions       → pattern hub
Demonstrations  → evidence record
Method          → ordered process
Company         → editorial institution
Start           → single-task preparation
```

The global system is coherent when these remain different while sharing:

```text
compact shell
surface-state language
typographic roles
status discipline
explicit closure
VertikALL Soul
```

This is stronger than using one component template for all routes.

---

# 15. Governing statement

> **Ink-VK should preserve donor coherence, not donor uniformity. A coherent target lets each route perform its own information job while making the governing experience system unmistakably shared.**
