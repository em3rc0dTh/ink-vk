# Ink-VK — Tactical Playbook v1.0

**Status:** FOUNDATION BASELINE CANDIDATE  
**Date:** 2026-08-14

> **Drone finds the terrain. Knife exposes the anatomy. Ink changes ownership. UTV moves the transformation in controlled slices. VK proves the result.**

## 1. Mission

This playbook is the field version of the Ink-VK framework. It converts the canonical 00–26 migration flow into a repeatable tactical strategy for a new entity.

It does not replace the evidence contracts. It tells an operator how to move through them without losing discipline.

## 2. Tactical assets

### DRONE — Reconnaissance

Use when the terrain is broad or uncertain.

Jobs:

```text
recover target
scan source landscape
compare candidates
identify missing evidence
map route/module topology
observe responsive/runtime states
```

The Drone collects. It does not decide the final transformation.

### KNIFE — Dissection

Use after a target or donor is recovered.

Jobs:

```text
separate page from job
separate expression from DNA
separate proof from claim
separate behavior from decoration
separate authorized reuse from imitation
identify assumptions
extract conditional principles
```

The Knife answers:

> What exactly is doing the useful work here?

### INK — Re-authorship

Use only after Target Truth, Soul, Replication Mode, and Transformation Contract exist.

Jobs:

```text
replace donor meaning with target meaning
re-author semantics
inject target operational reality
replace unsupported proof
change symbols / terminology / states
preserve intended fidelity without donor identity leakage
```

Ink is not a recolor pass.

### UTV — Controlled movement

Use during PLAN and BUILD.

Jobs:

```text
move one bounded slice at a time
carry only approved contracts
verify each slice before the next
avoid unplanned design detours
retain rollback / evidence path
```

The UTV does not sprint across unknown terrain.

### VK KIT — Validation

Use after each meaningful implementation slice and at campaign closure.

Checks:

```text
donor fidelity where required
Soul integrity
target truth
non-regression
provenance
cross-route/module coherence
```

## 4. Rules of engagement

### Rule 1 — Target first

Do not begin with donor admiration.

Begin with:

```text
what exists
what hurts
what works
what must survive
what is true
```

A donor is useful only relative to a defined target need.

### Rule 2 — Recover before critique

Do not redesign while recovering.

Observation and judgment are separate passes.

### Rule 3 — Evidence has rank

Prefer direct artifacts/runtime over interpretation.

Never promote `INFERRED` into `OBSERVED` without evidence.

### Rule 4 — Donor page is not atomic

A donor page may contain many jobs. Transfer jobs independently.

Example:

```text
pricing        OMIT
process        TRANSFER
FAQ            DEFER
closure        ADAPT
```

### Rule 5 — Fidelity is declared

Never use vague language such as:

```text
make it similar
make it like X
copy the vibe
```

Declare R1/R2/R3 and the exact dimensions that may match.

### Rule 6 — Target truth is the ammunition limit

The donor may show twenty records; the target may have one.

Design for future capacity, render current truth.

### Rule 7 — No invisible invention

When a donor slot has no supported target truth:

```text
REFRAME
REDUCE
OMIT
DEFER
```

not `INVENT`.

### Rule 8 — One semantic owner per strong device

Strong 3D, process geometry, evidence visualizations, editorial rails, or interaction modes require an information job.

Do not repeat a signature device everywhere merely for consistency.

### Rule 9 — Coherence is not sameness

The campaign should produce:

```text
ONE GOVERNING SYSTEM
+
MULTIPLE PURPOSE-SPECIFIC MODES
```

not a universal page/module template.

### Rule 10 — BUILD cannot redesign silently

A developer encountering an unresolved design-shaping decision must stop and reopen the relevant gate.

Implementation-safe tuning is allowed only inside the bounded design contract.

## 5. First-hour field procedure

When a new entity arrives:

```text
1. Open case workspace.
2. Record target authority and transformation goal.
3. Identify available direct evidence.
4. Recover the current entity at high level.
5. List unknowns without solving them.
6. Identify what must not regress.
7. Extract first Soul hypotheses, clearly marked as hypotheses.
8. Determine whether a donor is preselected or must be mined.
9. Do not choose replication mode from aesthetics alone.
10. Publish the first repository artifact before the case becomes chat-only knowledge.
```

## 6. Recon questions

### Target

```text
What exists today?
What is actually used?
What is only demo/prototype?
What is broken?
What already works well?
Who owns the truth?
What must survive?
What can change?
```

### Transformation

```text
What job must become stronger?
Is the need structural, experiential, technical, operational, or mixed?
What evidence would prove improvement?
```

### Donor

```text
What does the donor understand better than the target?
Which part is intelligence?
Which part is donor-specific business context?
Which part is mere visual expression?
Which part is proprietary implementation material?
```

## 7. Quarry screening procedure

For every serious candidate record:

```text
SOURCE
ROLE
WHY FOUND
TARGET NEED ADDRESSED
QUALITY
TRANSFERABILITY
RIGHTS / PROVENANCE
RISKS
REJECT REASON if rejected
```

Do not discard rejected candidates silently. Rejection teaches the mining model.

## 8. Knife procedure — donor dissection

For each major donor unit:

```text
1. What is visible?
2. What user/system job is being performed?
3. What makes it effective?
4. Is effectiveness structural, behavioral, semantic, or aesthetic?
5. What assumptions does it carry?
6. What target truth would be required?
7. What can transfer as DNA?
8. What expression must not transfer?
9. What would break if copied literally?
```

Then assign a DNA record.

## 9. Ink procedure

For every transferred DNA:

```text
DONOR PRINCIPLE
→ TARGET PROBLEM
→ TARGET SOUL
→ TARGET TRUTH
→ TARGET-SIDE INTERPRETATION
→ NEW EXPRESSION
```

A good Ink decision has a reason on both sides:

```text
WHY THIS DONOR INTELLIGENCE MATTERS
+
WHY THIS TARGET EXPRESSION BELONGS HERE
```

## 10. Blueprint ambush check

Before PLAN, actively hunt for hidden contradictions:

```text
Does one route/module upgrade truth another route keeps honest?
Are two sources competing for the same pattern?
Did one signature device spread everywhere?
Did responsive behavior change the information job?
Did a decorative decision become architecture?
Did an optional future capability become a present UI promise?
Did a static concept frame override a stronger contract?
```

If yes, close the contradiction before PLAN.

## 11. UTV procedure — migration slices

A valid slice is small enough to verify and large enough to preserve a complete semantic job.

Each slice carries:

```text
MISSION
INPUT AUTHORITY
TARGET STATE
DEPENDENCIES
DO-NOT-CHANGE BOUNDARY
ACCEPTANCE EVIDENCE
```

Avoid slices such as:

```text
make the whole site modern
add animations
refactor everything
clone donor header
```

Prefer:

```text
implement global shell behavior
implement Home hero operational network state
implement Method connected sequence
implement Start D0 presentation state
```

## 12. VK field procedure

Run the tests in order because later tests do not excuse earlier failures.

```text
21 Donor Parity
22 Soul Integrity
23 Truth / Claim / Dependency
24 Non-Regression
25 Mode-Aware VK
```

A beautiful target that invents capabilities fails.

A truthful target that lost the intended R3 experiential system fails donor parity.

A faithful donor clone that does not belong to the target fails Soul.

## 13. Stop / retreat conditions

Stop advancing when:

```text
BLOCKING UNKNOWN > 0
source rights are materially unclear for intended direct reuse
Target Truth cannot support the proposed job
stakeholder authority contradicts current Soul/Truth
new evidence invalidates a frozen baseline
implementation would require an unapproved architecture/design change
```

The correct move is gate reopening, not improvisation.

## 14. Fast path without shortcutting

Ink-VK may be executed quickly when evidence is strong.

Speed comes from collapsing documentation detail, not from removing control gates.

A small case may combine several outputs into one artifact if it still makes explicit:

```text
recovery
audit
Soul
truth
replication mode
donor evidence
DNA
transformation decisions
blueprint
validation
```

Do not confuse fewer files with fewer decisions.

## 15. Campaign commander board

At all times the case should answer:

```text
WHERE ARE WE?
WHAT IS AUTHORITATIVE?
WHAT IS BLOCKED?
WHAT IS UNKNOWN?
WHAT IS THE NEXT LEGITIMATE MOVE?
IS BUILD AUTHORIZED?
```

If these answers require searching old chats, repository control has failed.
