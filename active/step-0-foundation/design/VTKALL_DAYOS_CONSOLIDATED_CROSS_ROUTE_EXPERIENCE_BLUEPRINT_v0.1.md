# 1. Purpose

The route-level transformation phase is now provisionally closed for:

```text
HOME
SOLUTIONS
DEMONSTRATIONS
METHOD
COMPANY
START
```

Each route already has:

```text
target information job
donor page-mode input
target truth boundary
content-capacity boundary
non-regression obligations
route-level transformation decisions
```

The remaining design problem is no longer deciding what each page does in isolation.

It is deciding:

> **How do six individually valid routes become one coherent VertikALL experience?**

This document defines that cross-route experience system before PLAN or BUILD.

# 5. Cross-route page-mode system

The six routes must not share one section template.

They belong to six information modes:

| Route | Page mode | Primary user job | Dominant experience behavior |
|---|---|---|---|
| Home | Narrative choreography | Arrive, recognize, understand, choose | Large state changes + 3D + narrative pacing |
| Solutions | Pattern hub | Scan recurring business contexts | Broad-field pattern density + concrete demo path |
| Demonstrations | Evidence record | Understand one concrete example | Featured record + status/proof discipline |
| Method | Ordered process | Understand how VertikALL works | Connected sequence + process clarity |
| Company | Editorial institution | Understand mission, origin and philosophy | Long-form editorial hierarchy + local orientation |
| Start | Single-task preparation | Prepare one business-flow conversation | Focused compact task surface + minimal distraction |

### Cross-route invariant

```text
COHERENCE
≠
IDENTICAL LAYOUT
```

The shared system is expressed through:

```text
global shell
surface grammar
typographic roles
spacing logic
status grammar
motion hierarchy
route closure
brand expression
```

while route-specific information architecture remains different.

# 6. Global shell blueprint

## 6.1 Desktop shell

Canonical structure:

```text
VERTIKALL BRAND / HOME
        |
        |       [ SOLUTIONS  DEMONSTRATIONS  METHOD  COMPANY ]
        |                         compact nav field
        |
        |_______________________________________________ [ START ]
```

### Brand anchor

The official VertikALL mark remains target-owned.

Role:

```text
brand identity
home navigation
stable orientation
```

### Central navigation field

Use the donor principle of a compact persistent navigation field.

Current admitted informational routes:

```text
Solutions
Demonstrations
Method
Company
```

`Start` receives primary-action treatment rather than being visually equal to informational navigation.

This avoids duplicating the same route as both an ordinary nav item and a primary action.

### Primary action

```text
START
```

Target meaning:

```text
begin with one business flow
```

Not:

```text
Schedule Demo
Book now
Buy
Start trial
```

unless future target truth changes.

## 6.2 Dropdown / disclosure rule

Dayos uses compact dropdown disclosure.

Current VTKALL truth does **not** support enough admitted child routes to justify universal dropdown menus.

Therefore:

```text
COMPACT NAV GRAMMAR → TRANSFER
FAKE CHILD MENUS     → FORBIDDEN
```

A disclosure is activated only when a route has real child destinations or states.

## 6.3 Home navigation

The brand anchor acts as the Home destination.

No separate `Home` label is required in the primary nav unless later usability evidence justifies it.

# 8. Surface-state system

The donor repeatedly uses surfaces as narrative states rather than decorative card styling.

VTKALL should preserve that system role.

Define semantic surface classes rather than final hex tokens:

```text
S0 — WARM / NEUTRAL ARRIVAL CANVAS
S1 — DARK ASSERTION / MANIFESTO SURFACE
S2 — LIGHT EDITORIAL / DETAIL SURFACE
S3 — EVIDENCE / MECHANISM SURFACE
S4 — FOCUSED TASK SURFACE
S5 — GLOBAL FOOTER SURFACE
```

## 8.1 Current target color evidence

Existing VTKALL expression includes:

```text
warm canvas
ink / dark
amber
orange action
blue trust / structure
green growth / progression
```

These remain target-side candidates, not immutable final tokens.

## 8.2 Color-role rule

Strong accent color must have a job:

```text
action
selection
status
progression
semantic emphasis
```

Do not create multi-color decoration simply because the current palette contains several colors.

## 8.3 Handoff rule

A surface change must communicate one of:

```text
narrative phase change
proof transition
process transition
focused task entry
route closure
```

Rounded surface entry may reproduce the donor's handoff grammar.

Exact radius remains unresolved until Design Freeze.

# 9. Typography role system

Typography participates in composition.

Define roles:

```text
T-DISPLAY-XL   dominant route / manifesto statement
T-DISPLAY-L    major section claim
T-HEADING-M    structured section title
T-BODY         explanatory reading
T-META         labels / status / route identity
T-ACTION       CTA / control label
```

## 9.1 Cross-route behavior

Home and Company may use the strongest display scale.

Solutions and Method use strong display hierarchy but should prioritize scanning/process legibility.

Demonstrations uses proof/status hierarchy over theatrical type.

Start uses compact focus and should not reproduce Home-scale display mass inside the task surface.

## 9.2 Identity boundary

The exact Dayos font family is not a target asset.

The target typography must reproduce:

```text
authority
scale contrast
compact labels
readable body width
strong geometry
```

with a valid VertikALL type system.

Final font selection remains a Design Freeze item.

# 10. Spatial composition system

Global rule:

> **Wide field, controlled reading width, and every large empty field must have a compositional job.**

Avoid the original VTKALL failure pattern:

```text
cramped central content
+
unused lateral field
```

## 10.1 Allowed wide-field jobs

```text
3D stage
evidence visual
peer pattern matrix
process geometry
editorial orientation rail
status / metadata field
```

## 10.2 Reading width

Long-form prose remains controlled even when the overall page field is wide.

Company is the clearest example:

```text
wide system
+
narrow readable thesis columns
+
local orientation
```

## 10.3 Density

Density follows user job:

```text
Home            → narrative / varied
Solutions       → medium-to-dense scanning
Demonstrations  → evidence-focused
Method          → ordered / spacious enough to read progression
Company         → long-form editorial
Start           → compact single-task
```

No universal `section min-height` or `one viewport per section` rule is approved.

# 11. Motion grammar blueprint

Exact timing/easing is not yet recoverable from the static donor evidence.

The blueprint therefore freezes **motion classes and semantic jobs**, not invented milliseconds.

```text
M1 — GLOBAL NAV DISCLOSURE
M2 — SURFACE HANDOFF
M3 — CONTENT / TYPOGRAPHIC REVEAL
M4 — 3D AMBIENT / RESPONSE
M5 — PEER BROWSING / HORIZONTAL SHIFT
M6 — PROCESS PROGRESSION
M7 — FOCUSED TASK ENTRY / EXIT
```

## 11.1 Motion hierarchy

Motion must clarify:

```text
entry
state change
relationship
sequence
focus
selection
```

Motion must not manufacture:

```text
fake progress
fake processing
fake success
fake loading
fake system activity
```

## 11.2 Route allocation

| Route | Primary motion classes |
|---|---|
| Home | M2, M3, M4, contextual M5 |
| Solutions | M2, M3, optional M5 only for real peer browsing |
| Demonstrations | M2, M3; evidence motion only if source asset supports it |
| Method | M2, M3, M6 |
| Company | M2, M3; restrained editorial movement |
| Start | M7; no fake form-processing motion |

## 11.3 Reduced motion

Implementation must provide an equivalent reduced-motion state that preserves information and hierarchy.

This is a target accessibility requirement, not a claim about Dayos implementation.

# 19. Cross-route repetition control

A donor signature becomes weaker if every route uses it indiscriminately.

Allocate signature devices intentionally:

```text
HOME
owns strongest 3D + broadest narrative choreography

SOLUTIONS
owns dense pattern scanning

DEMONSTRATIONS
owns explicit evidence/status treatment

METHOD
owns connected sequence geometry

COMPANY
owns long-form editorial orientation

START
owns single-task isolation
```

Shared devices such as dark opener, rounded handoff and explicit closure may recur because they are system grammar.

Signature devices should recur only when the same semantic job exists.

# 24. Blueprint acceptance check

A consolidated blueprint passes only if:

```text
1. every route has a distinct information job;
2. the global shell does not imply unsupported route depth;
3. shared grammar creates coherence without one-template repetition;
4. signature devices are allocated by semantic job;
5. target truth / capacity / dependency ceilings survive cross-route composition;
6. original VTKALL UX failures are actively prevented;
7. evidence/status semantics stay consistent;
8. responsive transformation preserves order and meaning;
9. donor resemblance remains high in admitted experiential dimensions;
10. VertikALL Soul remains visible without relying only on logo/color replacement.
```
