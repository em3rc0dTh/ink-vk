## 1. Governing rule

> **3D is not a universal decoration system.**

For the current R3 case, major 3D belongs primarily to Home because that is where the target worldview and donor experience role genuinely align.

```text
HOME            → PRIMARY 3D OWNER
SOLUTIONS       → pattern/inventory composition
DEMONSTRATIONS  → evidence visuals first
METHOD          → process geometry
COMPANY         → editorial narrative
START           → focused task surface
```

# 2. Target semantic authority

The target Soul establishes:

```text
EVERYTHING IS A NETWORK
```

Native concepts include:

```text
network
node
flow
handoff
signal
path
connection
visibility
control
leverage
capacity
continuity
```

Therefore the Home 3D system is frozen as:

> **Operational Network / Flow Graph**

This is a semantic system, not a literal telecom/network diagram and not a donor cube replacement exercise.

---

# 3. Primary Home object

The Home hero receives one dominant conceptual network object.

Its visual job is to communicate:

```text
many operational elements
connected through flows / handoffs
whose structure can become clearer and more controllable
```

It must act as compositional counterweight to the hero statement without competing with readability.

### Required qualities

```text
calm
tactile
structured
precise
legible as relationships
non-intimidating
non-product-like
```

### Avoid

```text
cyberpunk spectacle
random floating primitives
AI-brain symbolism
enterprise-dashboard mimicry
telecom infrastructure literalism
machine activity implying live product state
```

---

# 4. Three semantic states

The object may carry three narrative transformations corresponding to the approved target taxonomy.

## ORGANIZE

Meaning:

```text
scattered nodes / flows
→ grouped or structured relationships
```

The viewer should read increasing legibility, not magical automation.

## FOLLOW UP

Meaning:

```text
pending / interrupted path
→ visible reconnection / continued signal
```

The viewer should read continuity and reduced dropped handoffs.

## CONTROL

Meaning:

```text
multiple relationships
→ coherent visible system state
```

The viewer should read oversight / visibility, not centralized surveillance or a live control dashboard.

These are conceptual metaphors. They are not product-feature screenshots and must never be presented as direct evidence of capabilities.

---

# 5. Relationship to evidence

Conceptual 3D and evidence are distinct UI classes.

```text
CONCEPTUAL 3D
= worldview / mechanism metaphor

EVIDENCE VISUAL
= target-owned artifact that supports a concrete claim
```

A 3D object must never be labeled or composed so that a visitor could reasonably interpret it as:

```text
real product UI
customer environment
production telemetry
live operating state
case-study proof
```

Demonstrations remains evidence-first even if Home uses strong 3D.

---

# 6. Motion relationship

The 3D system follows M4 from `VTKALL_DAYOS_MOTION_SPEC_v0.1`.

Allowed:

```text
subtle ambient movement
semantic state changes aligned with narrative progression
restrained pointer response
stable reduced-motion compositions
```

Forbidden:

```text
constant attention-seeking rotation
random state changes
fake processing
motion necessary to decode core content
```

---

# 7. Production boundary

Default production route:

```text
ORIGINAL TARGET-OWNED PRODUCTION
```

Allowed sources:

1. original geometry constructed from primitives;
2. procedural geometry created for VertikALL;
3. new in-house target-owned models;
4. third-party assets only when their license, source and permitted use are recorded before adoption.

### Explicitly forbidden without separate rights evidence

```text
Dayos raw/source 3D models
Dayos textures
Dayos proprietary shaders/code
Dayos source scene files
Dayos font files
reverse-extracted donor assets
untracked downloaded assets
untracked generated assets whose usage rights cannot be recorded
```

Experiential parity authorizes the **role** and **quality bar**, not donor asset possession.

---

# 8. Implementation technology boundary

No rendering library is selected in Design Freeze.

Current target implementation has no established 3D runtime dependency. PLAN must therefore treat 3D technology as an explicit implementation dependency rather than silently importing one during BUILD.

Selection criteria for PLAN:

```text
supports semantic states
supports reduced motion / static fallback
acceptable performance on target viewports
supports original target-owned assets
maintainable within the target stack
allows evidence capture for visual parity
```

Technology choice may not change the frozen semantic story.

---

# 9. Performance / fallback design boundary

The design must remain coherent if the full 3D runtime is unavailable or intentionally reduced.

Fallback must preserve:

```text
hero balance
network / flow meaning
Organize / Follow Up / Control conceptual distinction
reading hierarchy
route progression
```

A static or lightweight representation is therefore a valid fallback, not a failed state.

---

# 10. Implementation-safe unknowns

The following remain deliberately open to calibrated production:

