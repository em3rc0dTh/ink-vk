**Status:** PROPOSED / FOUNDATION ITERATION  
**Date:** 2026-08-14  
**Supersedes conceptually:** `INK-VK_MIGRATION_FLOW_v0.4.md`; prior versions remain preserved.  
**New learning source:** VTKALL Demonstrations × Dayos Use Cases

---

# 1. Why v0.5 exists

v0.3 introduced Target Truth.

v0.4 introduced Target Non-Regression.

The Demonstrations pass exposed a third independent architectural concern:

```text
THE TARGET CONTENT IS TRUE
BUT
THERE IS NOT ENOUGH OF IT
TO JUSTIFY THE DONOR MECHANISM
```

Example:

```text
DAYOS USE CASES
= filterable dense library

VTKALL DEMONSTRATIONS
= one concrete demonstration
```

A fake migration would preserve donor chrome by rendering:

```text
empty filters
fake cards
single-value categories
unnecessary pagination
```

A correct migration preserves the donor information job while adapting the mechanism to actual target capacity.

Governing rule:

> **Design for future capacity; render current truth.**

and:

> **Preserve donor information jobs; activate donor mechanisms only when target content capacity creates a real user need.**

---

# 2. Important architectural decision

v0.5 does **not** add another macro phase.

The framework should not improve by endlessly creating steps.

Instead, Content Capacity becomes an explicit authority inside the existing mapping, truth-gating, fidelity-contract, blueprint, and validation work.

This preserves a disciplined spine while strengthening decision quality.

# 4. Content Capacity authority

Companion methodology:

`methodology/INK-VK_CONTENT_CAPACITY_GATE_v0.1.md`

Content Capacity asks:

> **Does the target have enough real content and meaningful variability to justify this donor structure or interaction?**

This is separate from Truth.

Example:

```text
Turagua demo exists
→ TRUE

Turagua is the only current concrete demonstration
→ capacity does not justify a rich filter rail
```

# 5. Capacity states

Canonical working states:

```text
C0 — NO SUPPORTED CONTENT
C1 — SINGLE RECORD / SINGLE STATE
C2 — PEER SET
C3 — CLASSIFIABLE LIBRARY
C4 — DEEP MULTI-STATE SYSTEM
```

These states describe **information capacity**, not maturity quality.

A C1 target is not inferior.

It simply requires a different current rendering from a C3 donor.

# 7. STEP 14 — Route / Slot truth gate v0.5

The Target Truth Gate remains authoritative.

v0.5 adds a second question after truth:

```text
THE SLOT IS TRUE
↓
DOES CURRENT TARGET CAPACITY JUSTIFY THE DONOR MECHANISM?
```

Example:

```text
DEMONSTRATION RECORD = TRUE
FILTER BY INDUSTRY = NOT CURRENTLY USEFUL
```

Available mechanism dispositions:

```text
MATCH
REDUCE
REFRAME
OMIT
DEFER
```

These are separate from target truth dispositions:

```text
FILL
REFRAME
OMIT
DEFER
```

# 8. Interaction necessity contract

Every donor interaction must state the target-side reason it exists.

## Filter

Requires:

```text
multiple real values
+
meaningful user decision
```

## Carousel

Requires:

```text
peer set
+
sequential browsing benefit
```

## Tabs

Require:

```text
distinct target states or categories
```

## Comparison

Requires:

```text
multiple supported peers
+
valid comparison dimensions
```

## Pagination

Requires:

```text
inventory scale or performance/user-navigation need
```

A donor interaction without a target-side job is **decorative state complexity** and should not transfer.

# 9. Sparse-state equivalent

A key R2/R3 pattern is now formalized:

```text
DONOR DENSE MODE
+
TARGET C1 CAPACITY
=
SPARSE-STATE EQUIVALENT
```

The sparse-state equivalent preserves:

```text
route identity
surface grammar
record grammar
information hierarchy
entry / closure rhythm
proof discipline
future-safe system structure
```

while omitting volume-handling mechanisms that have no current job.

Example:

```text
DAYOS USE CASES
black opener
rounded handoff
filter rail
dense inventory

→

VTKALL DEMONSTRATIONS
black opener
rounded handoff
featured demonstration record
structured evidence detail
status guardrail
closure
```

# 10. Future-safe architecture rule

The target system may be designed to support future capacity.

Allowed:

```text
record schema supports many demonstrations
component can become peer grid later
filter model can be introduced later
```

Current UI must still render only current truth.

Therefore:

> **Future-safe architecture does not authorize fake-present UI.**

---

# 11. Capacity-aware donor parity

Donor parity must be interpreted at the correct abstraction level.

For collections:

### High-fidelity targets may include

```text
library identity
entry state
surface transitions
record-card grammar
metadata hierarchy
visual differentiation role
discovery orientation
```

### Literal parity may be invalid

```text
same record count
same filter count
same result density
same pagination depth
same number of categories
```

when target evidence differs.

Therefore:

> **R3 parity is experiential, not synthetic cardinality parity.**

# 12. Relationship among the four target authorities

## Soul

```text
What must belong to the target?
```

## Truth

```text
What may the target legitimately assert/show as real?
```

## Capacity

```text
How much real content/state exists, and what mechanisms does it justify?
```

## Non-Regression

```text
What known UX failures must not return, and what successes must survive?
```

These must not be collapsed.

Example:

```text
VTKALL DEMONSTRATIONS

Soul:
practical evidence / calm honesty

Truth:
Turagua is a demonstration

Capacity:
one concrete record

Non-Regression:
no clipped evidence cards or unresolved section mixing
```

# 14. STEP 18 — Blueprint admission v0.5

A blueprint now requires **six authorities**.

```text
1. DONOR FIDELITY
What donor jobs/states are matched?

2. TARGET SOUL
Why does this belong to the target?

3. TARGET TRUTH
What evidence supports every content-bearing slot?

4. TARGET CAPACITY
Does current content volume/variation justify every collection and interaction mechanism?

5. TARGET NON-REGRESSION
Which known target failures are prevented and which positive controls survive?

6. UNKNOWN BOUNDARY
What still cannot be specified without guessing?
```

If one authority is absent, blueprint is incomplete.

---

# 15. STEP 23 — Truth / Claim + Capacity check

After BUILD, Truth validation remains required.

v0.5 adds a capacity/interaction check:

```text
Does every filter have real alternatives?
Does every carousel have a real peer set?
Does every tab represent a real state/category?
Does every comparison contain real peers?
Does pagination/search solve a current need?
Are empty/fake placeholders used to simulate donor depth?
```

Results:

```text
JUSTIFIED
UNJUSTIFIED
NOT TESTED
NOT APPLICABLE
```

This does not require a new macro validation phase.

It is part of the Target Truth / Claim authority because both operate on content reality, while remaining a separately recorded sub-result.
