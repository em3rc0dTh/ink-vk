# Ink-VK — Migration Flow v0.6

**Status:** PROPOSED / FOUNDATION ITERATION  
**Date:** 2026-08-14  
**Supersedes conceptually:** `INK-VK_MIGRATION_FLOW_v0.5.md`; previous versions remain preserved.  
**New learning source:** VTKALL Method × Dayos Plans

---

## 1. Why v0.6 exists

v0.5 strengthened the framework with:

```text
Target Truth
Target Non-Regression
Content Capacity
```

The Method pass exposed another problem that does **not** require a new macro phase:

```text
ONE DONOR PAGE
CAN SERVE MULTIPLE UNRELATED JOBS
```

Dayos Plans contains:

```text
commercial decision
pricing comparison
selected plan emphasis
benefit/proof
process explanation
FAQ
conversion
```

VertikALL Method supports the process and route-level actions, but not pricing/plans/metrics/FAQ.

If mapping remains only at page level:

```text
DAYOS PLANS
↔
VTKALL METHOD
```

it is too easy to accidentally transplant unsupported adjacent jobs.

Therefore v0.6 adds **Donor Job Decomposition** inside existing donor dissection/mapping work.

Governing rule:

> **Match donor jobs, not donor pages as indivisible blocks.**

# 4. Why page-level matching is insufficient

Page-level matching may be directionally correct while still containing dangerous overreach.

Example:

```text
DAYOS PLANS
↔
VTKALL METHOD
```

is useful because both contain a process/decision journey.

But the donor also contains:

```text
pricing tiers
recommended plan
proof strip
FAQ
```

Those do not automatically belong to Method.

Therefore:

```text
PAGE FAMILY MATCH
≠
ALL SECTION JOBS APPROVED
```

# 6. Job admission order

For every donor job:

```text
1. TARGET JOB EXISTS?
2. TARGET TRUTH EXISTS?
3. TARGET CAPACITY JUSTIFIES IT?
4. INTERACTION HAS A REAL TARGET STATE?
5. CLAIM CEILING KNOWN?
6. NON-REGRESSION OBLIGATIONS SATISFIABLE?
```

Then:

```text
TRANSFER
REFRAME
OMIT
DEFER
```

The process is independent per job.

# 7. Anti-smuggling invariant

A valid donor match in one job cannot authorize adjacent jobs.

```text
PROCESS MATCH
≠ PRICING AUTHORIZATION

LIBRARY MATCH
≠ FILTER AUTHORIZATION

FORM MATCH
≠ SUBMISSION BACKEND AUTHORIZATION

COMPANY STORY MATCH
≠ PARTNER / TEAM METRIC AUTHORIZATION
```

This becomes a mandatory review question in composite donor mappings.

---

# 8. Partial transposition is valid R3

A donor route may have only a subset of jobs admitted.

Example:

```text
DAYOS PLANS

commercial opener      → REFRAME
pricing comparison     → OMIT
selected plan          → OMIT
benefit metrics        → OMIT / REFRAME PRINCIPLE ONLY
surface handoff        → TRANSFER
connected process      → TRANSFER HIGH
FAQ                    → DEFER
closing CTA            → TRANSFER / REFRAME
```

The target may therefore be structurally shorter.

This does not reduce the fidelity requirement for the jobs that remain.

Rule:

> **High fidelity for admitted jobs; zero fabrication for rejected jobs.**

---

# 9. Cardinality rule across job decomposition

Donor cardinality is never an automatic fidelity dimension.

Examples:

```text
4 donor process steps
≠ target needs 4 process steps

3 donor plans
≠ target needs 3 target options

12 donor use cases
≠ target needs 12 records
```

Fidelity should preserve the relevant system behavior:

```text
ordered progression
peer comparison
library discovery
```

only when target truth/capacity supports it.

---

# 10. Process job contract

A process job requires:

```text
real target states
+
real target order
```

If both are supported:

```text
connected geometry
progression states
step relationships
process navigation
```

may be admitted.

If only peer concepts exist without order:

```text
do not add arrows merely because donor has arrows
```

This distinction was validated across two VTKALL routes:

### Demonstrations

Multiple capabilities exist, but canonical order was unresolved.

```text
connected sequence → DEFER
```

### Method

Five steps and order are explicit.

```text
connected sequence → ADMIT HIGH
```

---

# 11. Proof job contract

Decompose proof into:

```text
PROOF ROLE
+
PROOF CONTENT
```

A visual emphasis strip can transfer if target has truthful content worth emphasizing.

Possible target content:

```text
verified metrics
verified status
verified capability
approved principle
```

But:

```text
donor quantitative proof
→ invented target quantitative proof
```

is forbidden.

---

# 12. Comparison job contract

A comparison job requires:

```text
2+ real peers
+
valid differentiating dimensions
+
meaningful user decision
```

Without these:

```text
comparison geometry → OMIT / DEFER
```

This prevents fake pricing/package matrices.

---

# 13. FAQ job contract

FAQ requires evidence of:

```text
real recurring question
+
approved answer
```

A donor FAQ does not authorize speculative policy or commercial copy.

If no FAQ truth inventory exists:

```text
FAQ → OMIT NOW / DEFER
```

---

# 14. Local navigation job contract

Local rails, tabs, choices, and anchors require multiple real destinations/states.

If the target page is a single linear process:

```text
DONOR LOCAL OPTIONS
→ REDUCE / OMIT
```

Do not invent target destinations to preserve interaction chrome.

---

# 15. Relationship with Content Capacity

Donor Job Decomposition asks:

```text
WHAT JOBS EXIST IN THIS DONOR PAGE?
```

Content Capacity asks:

```text
DOES TARGET HAVE ENOUGH REAL CONTENT/STATE
TO JUSTIFY THIS JOB'S MECHANISM?
```

Example:

```text
JOB = COMPARISON
TARGET = no plans
CAPACITY = C0
→ OMIT
```

Another:

```text
JOB = PROCESS
TARGET = five ordered steps
CAPACITY = C2 ordered set
→ TRANSFER
```

---

# 16. Relationship with Target Truth

Truth asks:

```text
IS THE TARGET FACT REAL / APPROVED?
```

Job decomposition asks:

```text
DO WE EVEN NEED THIS DONOR JOB?
```

A page can have true content and still not need a donor job.

Example:

```text
true Method principle
```

does not imply:

```text
pricing comparison
```

---

# 17. Relationship with Non-Regression

After job admission, the target audit remains active.

A correct process transfer can still fail if the new connected sequence:

```text
clips labels
creates meaningless empty fields
loses orientation across viewports
mixes CTA/footer states
```

Therefore decomposition happens **before** non-regression acceptance, not instead of it.

# 20. Blueprint admission v0.6

A route blueprint must now answer seven authorities:

```text
1. DONOR FIDELITY
What donor system behavior is matched?

2. DONOR JOB DECOMPOSITION
Which donor jobs were admitted or rejected?

3. TARGET SOUL
Why does this still belong to the target?

4. TARGET TRUTH
What evidence supports every content-bearing slot?

5. TARGET CAPACITY
Why are the rendered mechanisms necessary now?

6. TARGET NON-REGRESSION
What known failures are prevented?

7. UNKNOWN BOUNDARY
What cannot yet be safely specified?
```

No blueprint should proceed to Plan if those authorities are unresolved.

# 22. Method non-regression application

Known target failures:

```text
M01 whitespace imbalance + clipped copy
M02 unresolved next-section visibility
M03 five-step list clipping
M04 long continuation without clear process orientation
M05 dark state + CTA mixing
M06 previous state + CTA + footer collapse
```

v0.6 Method contract requires:

```text
wide field used intentionally
supporting copy readable
connected process remains oriented across its full length
multi-viewport is allowed when intentional
rounded handoff replaces accidental leakage
CTA and footer are explicit closing states
```
