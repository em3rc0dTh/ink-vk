## 1. Why v0.8 exists

The Start pass exposed a truth problem not fully covered by copy/claim checks:

```text
AN INTERFACE CAN LOOK OPERATIONAL
WITHOUT THE TARGET SYSTEM BEING OPERATIONAL
```

Examples:

```text
form without submission
calendar without availability
success state without verified effect
search field without search capability
```

v0.8 therefore integrates the new contextual methodology:

`methodology/INK-VK_INTERACTION_DEPENDENCY_TRUTH_GATE_v0.1.md`

Governing rule:

> **Transfer interaction choreography only up to the highest target dependency state that is actually supported.**

## 4. Functional dependency ladder

Interactive targets may be classified using:

```text
D0 — PRESENTATION / SCHEMA ONLY
D1 — LOCAL INTERACTIVE STATE
D2 — VALIDATED LOCAL STATE
D3 — SUBMISSION / TRANSPORT
D4 — DELIVERY / PERSISTENCE / INTEGRATION
D5 — ACKNOWLEDGED DOWNSTREAM OUTCOME
```

The ladder is a capability ceiling, not a maturity score.

A disclosure interaction may truthfully stop at D1.
A preparation form may stop at D0.
A local calculator may reach D2 without external transport.

## 5. STEP 05 refinement — functional truth baseline

For interactive target areas record:

```text
CURRENT DEPENDENCY LEVEL
SUPPORTED USER STATES
MISSING DEPENDENCIES
IMPLIED USER-PROMISE CEILING
PROMOTION TRIGGER
```

Example:

```text
VTKALL START
current = D0
supported = read / understand / prepare / navigate
unsupported = submit / deliver / confirm / schedule
```

---

## 6. STEP 11 refinement — donor affordance recovery

Do not collapse donor visual evidence into assumed functionality.

Record separately:

```text
OBSERVED AFFORDANCE
VERIFIED DONOR BEHAVIOR
INFERRED DONOR BEHAVIOR
UNKNOWN DONOR BEHAVIOR
```

A screenshot containing a submit button proves a visible submit affordance.
It does not by itself prove successful transport, validation, delivery, or acknowledgement.

## 8. STEP 14 refinement — interaction admission

For each affordance ask:

```text
1. Does the target user job exist?
2. Is the content/state true?
3. Does target capacity justify it?
4. What does the control promise?
5. What dependency level does that promise require?
6. Does the target meet that level?
7. Are downstream dependencies known?
8. Can non-regression obligations be satisfied?
```

Then choose:

```text
TRANSFER
REFRAME
REDUCE
OMIT
DEFER
```

## 13. STEP 20 refinement — no silent promotion during BUILD

If the approved target state is D0, BUILD may not silently add:

```text
hidden form submission
persistence
external delivery
fake success
background side effects
```

Any functional promotion requires an updated truth/dependency contract first.

Implementation convenience does not raise the target claim ceiling.

---

## 14. STEP 23 refinement — functional truth validation

For every enabled control:

```text
WHAT DOES IT PROMISE?
↓
CAN THE TARGET SYSTEM COMPLETE THAT PROMISE?
↓
IS THE RESULT VERIFIABLE?
```

Possible validation results:

```text
PASS
OVERCLAIMS CAPABILITY
DEPENDENCY UNVERIFIED
HIDDEN SIDE EFFECT
NOT TESTED
```

A donor-parity pass cannot override a functional-truth failure.

---

## 15. Success-state rule

A success message is a claim about a real effect.

Require:

```text
SUCCESS MESSAGE
TRIGGER
DOWNSTREAM EFFECT
VERIFICATION SOURCE
FAILURE ALTERNATIVE
```

If no verifiable effect exists:

```text
SUCCESS STATE → DEFER
```
